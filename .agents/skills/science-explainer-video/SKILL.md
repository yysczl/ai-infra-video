# Science Explainer Video｜科普视频制作

## 核心定位

把科普视频制作成**一部有旁白的动画纪录片**，而不是一份自动播放的 PPT。

旁白负责讲述和解释，画面负责让观众看见正在发生的事情。观众应该能看到用户如何操作、请求如何流动、数据如何变化、设备如何执行、系统如何响应，再通过旁白理解背后的技术原理。

制作时始终遵循：

1. **先确定观众应该看到什么，再设计旁白和动画。**
2. **先展示具体对象与过程，再抽象出术语、机制和架构。**
3. **一个场景围绕一个主要教学问题展开。**
4. **一段包含多个事件的口播，必须有相应的视觉发展；不能长期用一张静态图承载所有内容。**
5. **动画服务于理解，不以动画数量、复杂程度或视觉炫技作为质量指标。**

## 默认交付

最终默认只交付两项：

1. **完整口播稿**：优先 Markdown，逐字可读，带必要的场景/步骤锚点和动画触发提示。
2. **可运行的 HTML 课件项目**：包含入口 HTML、必要的 CSS、JavaScript、SVG/Canvas、素材及运行配置；小项目可单文件，大项目可保留工程目录。

默认不生成独立分镜文档、术语词典、设计报告、审稿报告、参考资料汇编、PPT、PDF、额外 README 或演示视频。必要的同步信息、术语解释和来源记录直接放在口播稿或项目内容源中。用户明确要求时再增加其他交付物。ZIP 仅作为项目打包方式，不算第三类交付。

如果用户只要求制作/修改 Skill、只要口播稿、只要 HTML 或只要求审查，严格遵循其指定范围，不擅自补齐其他产物。

## 一、知识组织与受众

- 默认以公众和初学者为基准；不要把创作者熟悉的某个细分方向误当成大众的知识起点。
- 先确定视频要回答的核心问题，再组织知识结构。行业全景应覆盖主要生命周期和角色，不机械罗列名词。
- 核心术语说明：是什么、解决什么问题、为什么需要、基本如何工作，以及与相邻术语的关系。
- 用一个或少数几个能追踪变化的案例串联内容，例如用户请求、数据、模型、设备或真实现象。不要强行让一个类比解释所有知识。
- 时长决定深度。不要靠提高语速把太多概念塞进短视频；必要时拆分内容或明确范围。
- 技术准确性优先于故事效果。简化模型、模拟数据和示意动画必须明确标识，不能让观众误以为是通用规律或实测结果。

## 二、动画纪录片式叙事

### 2.1 先设计观众看到的事件

在写口播或制作页面之前，先明确每个主要教学片段：

- 观众此刻看到什么对象？
- 对象正在做什么？
- 状态如何变化？
- 变化产生什么结果？
- 这个过程揭示了什么问题或机制？
- 何时适合从具体场景转向局部原理或系统全景？

不要先写一大段旁白，再把旁白压缩成几个抽象标签贴到页面上。

### 2.2 一个场景只承担一个主要教学任务

一个场景可以包含多个连续步骤，但应围绕一个主要问题或一个完整过程展开。例如：

- “一个用户如何完成一次 AI 问答？”
- “多个请求同时到达时，服务端如何处理？”
- “CUDA 线程如何映射到数组元素？”
- “KV Cache 如何随着 Token 生成而增长？”

如果一段内容同时包含多个独立教学目标，例如请求进入、排队、TTFT、增加 GPU、成本、调度和课程路线，不要全部挤在同一场景。根据逻辑关系拆成多个场景，或重新安排章节顺序。

不要为了维持原有页数而压缩知识。也不要为了拆分而把完整、简单的解释切得过碎。拆分依据是教学任务和因果过程，不是句子数量。

### 2.3 口播长度必须有相应的视觉发展

当口播描述多个事件、操作或状态变化时，画面应随着事件推进，展示相应的变化。例如：

- 用户输入问题 → 点击发送 → 请求离开客户端 → 模型生成 → 回答出现。
- 多个请求到达 → 服务入口接收 → 请求排队 → 部分请求执行 → 请求完成。
- Token 逐个生成 → K/V 写入缓存 → 后续步骤复用历史缓存。

不允许一段口播连续讲述多个不同事件，而画面始终停留在一张只展示最终结论的静态图上。

但静止画面本身并不是问题。如果旁白正在解释同一个稳定结构、参数含义或已经展示的结果，保留画面供观众观察通常更好。判断标准是内容是否发生了新的、值得展示的变化，而不是旁白持续了多少秒。

### 2.4 纪录片式镜头语言

根据知识内容选择镜头组织方式，不强制套固定模板：

- **建立场景**：先让观众知道人物、产品、设备或系统处于什么情境。
- **跟随动作**：跟随一次点击、请求、数据传递或设备操作。
- **局部特写**：放大队列、代码行、线程、缓存块或某个关键状态。
- **过程观察**：展示数据、任务或资源随时间变化。
- **对照镜头**：在相同条件下比较两种实现或两种状态。
- **拉远与揭示**：从局部操作拉远，展示它属于哪个系统或架构。
- **总结镜头**：把刚才看到的过程整理为技术关系或关键结论。

这些是可用的叙事手段，不是每个场景都必须依次使用的镜头清单。不要为了“纪录片感”添加无意义的运镜、粒子或装饰效果。

### 2.5 具体过程之后再抽象

优先顺序通常是：具体情境 → 操作/事件 → 过程变化 → 结果与因果 → 技术术语/原理 → 系统全景。

这不是僵化模板。对于适合直接解释的数学定义、硬件结构或算法概念，可以直接从图示开始；但如果旁白讲的是具体事件，画面就不能只给抽象架构图。

## 三、场景拆分与信息密度

### 3.1 场景、口播片段和动画步骤

- **场景 Scene**：围绕一个主要教学问题或完整过程。
- **口播片段**：围绕一个语义完整的解释单元，可以是一句话，也可以是连续几句话。
- **动画步骤/状态**：呈现一个关键状态或推进一个可观察变化。
- **连续动画**：可以在某个步骤中持续运行，不要求每个运动都成为独立步骤或独立 ID。

一个场景可以有多个口播片段和多个动画步骤，但不要让单个状态承担多个彼此独立的教学任务。

### 3.2 什么时候应该拆分

出现以下情况时，优先考虑拆分场景或重新组织：

- 口播从一个主题跳到另一个独立主题。
- 同一段口播连续解释多个不同的因果链。
- 观众需要同时理解多个新对象、新术语和新机制。
- 需要从具体案例转向另一种独立技术原理。
- 一张图必须同时展示多个阶段，导致元素拥挤或难以追踪。

可拆成多个场景、多个页面，或在现有场景中安排连续的镜头变化。选择对观众最清楚、对现有工程最稳妥的方式。

### 3.3 不要机械追求“一句话一个动作”

- 一个动作可以覆盖数句口播。
- 多个视觉变化可以在同一个步骤内连续发生。
- 一段解释可以保持画面不动。
- 关键事件必须有视觉对应，但不要求每句话都有独立动画。
- 如果页面状态数量受项目约束，应优先在现有状态中组织连续动画，或增加场景/页面；不要擅自突破验证器约束。

### 3.4 信息密度检查

每个场景完成后，检查：

- 观众能否用一句话说出本场景主要解释的问题？
- 是否同时引入了过多新术语？
- 是否有一段口播包含多个独立事件，却没有对应的视觉变化？
- 当前画面是否需要观众自己脑补关键操作？
- 是否能把次要知识移到后续场景，而不影响当前理解？

如果一个场景很难用一句话概括其教学任务，通常需要重新组织。

## 四、自然口播与文案

把自己当成真正理解技术、正在向观众解释的人。说清楚谁做了什么、处理了什么、为什么会这样。

避免：
- 用口号冒充解释，例如“沿着职责，把工具放回系统”。
- 机械对仗和重复句式，例如连续使用“从 A 到 B”“不只是 A，更是 B”。
- 抽象词堆叠，例如“赋能、打通、承载、塑造、驱动”，却没有具体对象和动作。
- 把正常解释拆成大量三四字短句。
- 无意义的反复澄清、防御性表达、装饰性英文栏目和每页强行金句。

标题和图示标签可以简短；逐字口播必须自然、完整、可朗读。口播不要简单复述屏幕上的字，也不要为了适配空洞画面而把具体讲解改成抽象套话。

类比可以帮助理解，但之后要回到准确的技术定义。详细编辑检查见 `references/script.md`。

## 五、视觉设计与 HTML 动画

### 5.1 视觉语言统一，页面构图不模板化

- 沿用用户认可的设计语言；改文案或局部动画时不随意推倒成熟视觉系统。
- 不同知识点使用适合自己的表现方式，不要所有页面都变成“左标题、右卡片、底部金句”。
- 主视觉优先展示对象、状态、数量、路径、动作和因果，不让矩形和箭头只充当文字容器。
- 适当使用界面模拟、实体示意、数据流、代码联动、时间轴、对照和架构图。
- 动画必须帮助观众追踪变化。避免只靠淡入、缩放、粒子和无意义移动制造“动效”。
- 保证 16:9 / 1080p 等目标录制分辨率下文字与图形清晰可读。

### 5.2 选择合适的视觉形式

- **应用与产品流程**：简化软件界面、用户操作、输入输出和请求路径。
- **GPU 与计算**：芯片/计算单元示意、线程与数据映射、数组/矩阵变化、显存读写。
- **编程框架和工具**：真实短代码、代码高亮、输入数据、执行过程和结果。
- **内存与数据结构**：数据块分配、缓存写入/读取、容量变化和数据传输。
- **系统与分布式架构**：节点、请求、队列、网络路径和故障恢复过程。
- **性能优化**：时间轴、吞吐量、延迟、资源利用率和优化前后对照。

不是每个页面都需要拟真 UI、代码或复杂动画。选择最有助于理解的方式。

### 5.3 代码是教学证据，不是装饰

介绍 PyTorch、CUDA、Triton、vLLM 等工具时，可选一个共同任务展示不同抽象层次。让观众看到输入、关键代码、数据/线程如何变化和输出结果。

- 只显示必要的核心代码，通常 5–10 行以内。
- 代码行应与图形或数据状态联动。
- 省略初始化或辅助代码时明确标注“核心片段/省略部分”。
- 伪代码必须明确标注，不得冒充可运行代码。
- 不暗示不同工具是互斥或完全平行的技术层。

### 5.4 示意、模拟和真实数据

模拟界面、模拟请求和模拟指标应标明“演示”或“示意”。不能将教学假设说成真实系统的固定行为。例如“GPU 一次只能处理四条请求”只能在明确的简化假设下使用，不能表述为 GPU 的普遍限制。实际能力取决于模型、批处理、序列长度、显存、调度策略和硬件等因素。

详细 HTML 实现与验收见 `references/html.md`。

## 六、口播与 HTML 的语义同步

口播是叙事主线，HTML 必须展示口播中的关键对象、动作、状态变化和结果。**锚点一致不代表语义一致，时间同步也不代表画面讲的是同一件事。**

对每个关键口播片段检查：

1. **对象**：口播说到的主要对象是否出现在画面中？
2. **动作**：口播描述的操作是否发生？
3. **结果/因果**：操作带来的状态变化是否可见？
4. **抽象时机**：是否先让观众看懂具体过程，再引入术语和架构？
5. **视觉节奏**：口播包含多个事件时，画面是否有相应发展？若内容没有新变化，是否有意保留静止观察？

如果口播提到了具体对象、操作或结果，而画面没有相关内容，优先补足画面；只有口播本身不准确、不清楚或顺序不合理时，才调整口播。

### 锚点和内容源兼容

- 沿用已有项目的场景 ID、步骤 ID、初态定义和 URL 映射，禁止为了统一示例格式而批量改名。
- 已有项目可能使用 `S07.0` 表示初态、`S07.1`–`S07.3` 表示后续步骤，并使用 `#S07/3` 定位；继续遵循项目实际约定。
- 新项目可选择 `Sxx-Axx`、`Sxx.step-x` 或其他一致格式，不强制某一种。
- `course.json` 等结构化内容源如果是项目的单一编辑源，应继续使用；不要另建一套需要手动维护的口播源。
- 若项目固定每页四个状态（含初态），增删内容时必须同步检查内容模型、导出脚本、校验器、渲染逻辑和旧链接。不要仅为了拆分口播而破坏既有协议。

### 播放控制

优先复用现有下一步/上一步、页面切换、暂停、整页重播、步骤条、URL 定位和录制模式。已有能力满足实际需求时，不强制增加动作 ID 输入、单步重播或独立 Timeline 控件。录制模式隐藏讲师备注、调试信息和非必要控件。

对逐条显示字幕的课件，分别记录动画状态和该状态内的字幕位置。一个动画状态可以对应多条字幕。状态内换字幕时沿用当前画面和动画时间线，保留原有状态 ID、顺序和定位方式。交互与显示细节见 [HTML 实现规范](references/html.md#逐条字幕)。

## 七、执行流程

### 新项目

1. 明确受众、时长、核心问题和课程范围。
2. 组织完整知识主线，并选择一条或少数几条可追踪的案例线索。
3. 先设计每个场景中观众应该看到的对象、事件、动作、结果和因果，再安排讲解顺序。
4. 检查每个场景是否只承担一个主要教学任务；拆开过载场景。
5. 编写自然、完整的逐字口播，并标注必要的场景/步骤锚点。
6. 制作 HTML，让画面呈现口播中的关键事件和技术机制。
7. 检查口播与画面的语义匹配、视觉节奏和抽象时机。
8. 实际运行并检查初态、中间态、终态、重播、跨页恢复和录制模式。
9. 只交付完整口播稿和 HTML 项目。

### 修改既有项目

1. 阅读现有源码、口播、内容源、README/AGENTS 规范、同步/校验脚本和播放器，先理解项目协议。
2. 逐页审查教学任务、口播信息密度、视觉叙事和锚点映射。不要只检查编号。
3. 区分问题属于知识结构、口播、视觉、动画、叙事节奏、语义同步还是工程实现。
4. 优先修复“一段口播包含多个事件，但画面长期静止或只有抽象图”的问题；补足具体场景、操作和状态变化。
5. 对承载多个独立教学目标的场景进行拆分或重新排序，不要为了保持原页数而塞内容。
6. 保留成熟视觉设计、内容源、锚点、初态、URL、步骤数约束和播放器功能。确需改动时，同步更新相关脚本与验证逻辑。
7. 实际运行检查关键状态和录制画面，交付更新后的口播稿与 HTML 项目。

## 八、发布前验收

不生成独立审查报告，但内部必须检查：

- **知识结构**：每个场景是否有清晰的主要教学问题？是否存在一个场景承担太多独立知识点？
- **口播密度**：一段口播是否连续讲了多个事件？这些事件是否有足够的视觉发展？
- **视觉叙事**：对象、动作、结果和因果是否可见？是否过早切换到抽象图？
- **节奏**：是否有不必要的频繁切换？是否给复杂画面留出观察时间？是否存在长时间静态画面却持续讲述多个新事件？
- **技术准确性**：定义、架构关系和运行机制正确；模拟与实测区分；无虚构性能收益。
- **文案**：自然、具体、可朗读；无口号式短句、机械对仗和空泛抽象表达。
- **工程兼容**：内容源、锚点、步骤映射、URL、校验脚本和播放器功能正常。
- 逐条字幕课件需在目标画布上检查文字是否完整显示，并验证字幕与动画在各播放模式下的推进顺序。
- **运行质量**：实际预览关键初态、中间态、终态、重播、跨页恢复和录制模式；检查遮挡、溢出和 1080p 可读性。无法实际运行时如实说明，不得虚报测试通过。
