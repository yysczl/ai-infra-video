# 口播、知识组织、场景拆分与叙事节奏

## 1. 从观众的问题出发

- 明确受众基础、常见误解，以及视频最后能解释的核心问题。
- 大众入门内容先建立全景和基本关系，再逐步深入；不要把创作者的专业方向当作默认知识起点。
- 每个核心术语解释：是什么、解决什么问题、为什么需要、基本如何工作，以及和相关术语的关系。
- 对比不等于对立。不同工具可能跨层使用或共同组成系统，不要画成互斥或必经路径。
- 选择一条或少数几条可追踪的案例线索。案例必须能帮助解释技术，不要强行用一个类比解释所有概念。

## 2. 把视频当作动画纪录片来写

口播不是对着页面逐项念标签，而是沿着一个可理解的过程讲述。写稿时先确定观众将看到什么，再安排讲解。

每个主要教学片段先回答：

1. 观众看到什么对象或场景？
2. 正在发生什么事件？
3. 对象或系统状态如何变化？
4. 变化带来什么结果？
5. 这一过程揭示了什么技术问题或机制？
6. 何时适合引入术语、局部原理或整体架构？

可采用但不强制的叙事顺序：建立场景 → 事件发生 → 跟随关键过程 → 展示结果/因果 → 解释技术原理 → 总结系统关系。

如果知识点适合直接定义或图解，不必硬编故事。动画纪录片式表达的重点是事件、过程和因果清楚，不是每段都要有人物或戏剧冲突。

## 3. 场景拆分：一个场景，一个主要教学问题

一个场景可以包含多个连续动作，但应围绕一个主要教学任务。例如：

- 一个用户如何完成一次 AI 问答？
- 多个请求同时到达时，服务器如何处理？
- CUDA 线程如何找到自己负责的数据？
- KV Cache 如何随着 Token 生成而变化？

如果一段内容同时讲请求进入、排队、TTFT、扩容、成本、调度和课程路线，说明场景承载过多，应按知识关系拆分或重新排序。

拆分时注意：
- 按教学目标和因果链拆，不按标点符号拆。
- 不为维持旧页数而把多个独立问题硬塞在一起。
- 不把一个简单、连贯的解释切成大量碎片。
- 若已有项目的页面状态数固定，优先考虑增加场景/页面，或在既有步骤中安排连续动画；只有确有必要并且工程允许时才调整状态数。

## 4. 口播时长与画面发展

如果口播描述多个事件，画面应有相应的发展。例如：

“用户输入问题 → 点击发送 → 请求离开客户端 → 模型开始生成 → 回答逐步出现。”

不应让旁白连续讲述这些不同事件，而画面一直停留在只展示最终状态的静态图上。

但不要用秒数机械决定动画数量：
- 画面不变、旁白继续解释同一结构或概念时，可以保持静止。
- 复杂图示出现后，应给观众时间观察。
- 口播描述新的对象、动作、数量、状态或因果时，考虑通过画面变化呈现。
- 一个动作可以覆盖多句话；一个步骤也可以启动一段连续动画。
- 不要求每句话都触发动画。

## 5. 镜头与叙事节奏

根据内容选择合适的视觉叙事方式：

- **建立场景**：让观众知道人物、产品、设备或系统处于什么情境。
- **跟随动作**：跟随一次输入、点击、发送、请求传递或设备操作。
- **局部特写**：放大关键队列、代码行、线程、缓存块或数据变化。
- **过程观察**：让观众看到任务、数据或资源随时间变化。
- **对照**：在相同条件下比较不同方案或状态。
- **拉远/揭示**：从局部操作拉远，展示其所属的系统和架构。
- **总结**：将已经看到的过程抽象为术语、关系或结论。

不要把这些做成固定的七步模板，也不要为了镜头感添加无意义的转场、粒子和运镜。

## 6. 去 AI 腔编辑测试

检查每页标题、旁白和图中标签：

1. 删掉这句，观众是否会丢失有效知识？没有就删除或替换。
2. 能否指出明确的对象、动作与结果？不能就具体化。
3. 连续几页标题是否重复同一种押韵/对仗句式？调整为问题型、说明型和少量强调型混合。
4. 真实讲师会在科普视频中这样说吗？如果像宣传册就重写。
5. 英文是专业术语，还是没有信息价值的装饰？后一类减少。

| 模板化文案 | 更具体的说法 |
| --- | --- |
| “沿着职责，把工具放回系统。” | “看看这些技术分别用在系统的哪个环节。” |
| “算法塑造能力，基础设施承载价值。” | “模型负责处理输入和生成结果，基础设施负责让模型在服务器上运行并对外提供服务。” |
| “从计算走向智能，从硬件走向未来。” | 直接说明当前章节讨论的硬件、计算过程或模型服务。 |

不要把所有短句都判为 AI 腔。标题和技术标签可以精炼；问题是用模糊短句代替解释。

## 7. 口播与画面的语义同步

同步检查不止是编号一致。对每个关键片段，确认：

- **对象**：口播说到的主体是否出现在画面？
- **动作**：口播描述的操作是否发生？
- **结果/因果**：操作带来的变化是否可见？
- **抽象时机**：观众是否先看到了具体过程，再理解术语和架构？
- **视觉节奏**：口播包含多个事件时，画面是否相应发展？静止是否是有意的观察停顿？

如果口播讲“用户在聊天框输入问题，点击发送，模型生成回答，随后更多用户同时使用”，画面应能呈现聊天输入、发送动作、回答生成、镜头拉远出现更多用户，以及请求进入服务系统。不能只用“1 个请求”的数字和几个装饰图形替代整个过程。

## 8. 锚点与内容源

- 沿用现有项目的场景 ID、步骤 ID、初态定义和 URL 映射。
- 例如 `S07.0` 是初态、`S07.1`–`S07.3` 是后续步骤，继续按项目协议使用；不强制迁移到 `Sxx-Axx`。
- 新项目可选一种一致格式，并明确初态与手动步骤。
- 如果 `course.json` 等结构化文件是统一编辑源，继续沿用；不要同时手动维护多套口播与页面数据。
- 口播中的触发标记不是读出来的台词。只在需要推进画面时标注，不要给每句话加编号。
- 一个动作完成后若需要观察，写明“保持画面”即可，不要为了有动作而添加无意义步骤。

## 9. 内容源与时长

口播全文必须可直接朗读。总时长应考虑自然讲解速度、连续动画运行和观察停顿。不要用语速硬塞内容。

如果项目以结构化数据为统一编辑源，口播 Markdown/Word 和浏览器数据由脚本生成，应继续使用该流程。默认只交付口播稿和 HTML 项目，不另生成分镜文件、术语表或审查报告。
