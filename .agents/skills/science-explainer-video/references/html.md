# HTML、动画纪录片式视觉叙事与工程验收

## 1. 技术选型与交付

- 优先轻量、完整、可编辑：一般项目使用 HTML/CSS/JavaScript + SVG；复杂交互可使用 Canvas、GSAP、React 等，但避免无必要的依赖。
- 小项目可单文件；较大项目保留清晰工程目录。HTML 项目包含运行必需的 CSS、JS、图形素材和配置。
- 若可直接打开 `index.html`，提供该入口；若需要开发服务器，保留必要配置并给简短启动命令。
- 不为了制作动画纪录片而默认引入视频剪辑时间轴、独立 Timeline 数据结构或复杂播放器。先检查现有实现能否完成教学表达。

## 2. 画面叙事：先让事情发生

HTML 不应只是口播稿的视觉标题页。它需要呈现关键对象、事件、操作、状态变化和结果。

- 口播从具体产品或生活场景开始时，优先展示简化界面、人物/设备、输入输出或实际操作。
- 先让操作发生，再展示结果；之后再通过镜头拉远、局部放大、路径高亮或结构转换揭示系统。
- 口播说用户输入、点击、发送、等待、收到结果，画面就应尽量展示这些动作。
- 口播说请求数量增加、队列变长、显存被占用或服务故障，画面应呈现相应变化。
- 口播解释因果时，尽量在连续画面中展示原因与结果之间的联系。
- 不要让抽象架构图过早替代观众尚未看见的具体过程。
- 不是每页都要做成拟真 UI。硬件可用实体结构，算法可用数据变化，系统架构可用节点和路径，代码可用高亮与执行映射。

## 3. 场景拆分与视觉节奏

### 一个场景，一个主要教学任务

每个场景应围绕一个主要问题或一条完整因果链。若一个场景同时要解释多个独立问题，考虑拆分成多个场景/页面，或重新组织内容。

### 不要一张图承载多个事件

如果口播连续描述多个事件或状态变化，画面必须提供足够的视觉发展。例：

1. 用户输入问题。
2. 用户点击发送。
3. 请求进入服务入口。
4. 模型开始生成。
5. 回答逐步出现在聊天窗口。

不要只显示一张最终的系统图，然后用几十秒旁白解释全部过程。

### 允许静止观察

画面不必持续运动。以下情况适合保持静止：

- 旁白正在解释已经展示的同一结构。
- 观众需要时间阅读代码、图表或复杂架构。
- 当前状态本身就是需要观察的结果。
- 没有新的对象、动作或状态变化需要呈现。

判断动画是否必要，要看是否有新的教学信息，而不是只看时间长度。

### 镜头方式按内容选择

可以使用建立场景、跟随动作、局部特写、过程观察、方案对照、拉远揭示和总结镜头。它们是可组合的手段，不是固定模板。运镜应帮助观众追踪对象或理解关系，不做纯装饰。

## 4. 适合不同内容的表现形式

| 内容 | 优先考虑的视觉方式 |
| --- | --- |
| 用户与产品交互 | 简化界面、输入、点击、发送、输出 |
| 请求与服务流程 | 请求流动、服务入口、队列、执行与完成 |
| GPU 并行计算 | 线程与数据元素映射、并行执行、结果写回 |
| 编程框架/工具 | 同一任务的短代码对比、代码高亮、输入输出联动 |
| 显存与缓存 | 数据块分配、写入、读取、复用、容量变化 |
| 分布式系统 | 多节点、网络传输、任务分配、故障与恢复 |
| 性能优化 | 时间轴、吞吐量、延迟、资源占用、优化前后对比 |
| 系统架构 | 在观众理解组件后，再用全景图总结职责和路径 |

不要让所有页面套用相同的“左标题 + 右卡片 + 底部结论”构图。保留系列视觉语言，但根据教学任务变化画面组织方式。

## 5. 动画设计

重要场景至少明确：

- 初始状态是什么？
- 关键事件发生时，哪些对象变化？
- 变化的先后顺序是什么？
- 最终状态是什么？
- 观众应从变化中理解什么？
- 回退、重播或重新进入时，状态如何恢复？

适合的动画包括：
- 对象从一个位置移动到另一个位置，展示真实的数据或请求路径。
- 数量、队列长度、资源占用随操作改变。
- 代码高亮与执行对象同步。
- 镜头从产品交互拉远至服务架构。
- 同一条件下展示两种方案的差异。
- 任务完成、资源释放、故障发生与恢复。

纯文字淡入可以用于引入标题或辅助信息，但不能代替技术过程。避免无意义的粒子、闪烁、弹跳和持续运动。

## 6. 代码、数据和技术机制联动

介绍编程工具时，可选择共同任务（例如向量相加），展示：

1. 输入数据与目标结果。
2. 简短、真实的核心代码。
3. 代码行与数据/线程/执行步骤之间的对应关系。
4. 输出结果。

要求：
- 代码通常只展示 5–10 行关键内容。
- 高亮代码时同步高亮对应数据或线程。
- 省略初始化、错误处理或辅助部分时，标注“核心片段/省略部分”。
- 伪代码必须明确标注。
- 不要把长代码当作装饰贴满页面。

讲 KV Cache 时，展示 Token 生成、K/V 写入和历史缓存复用；讲 Continuous Batching 时，展示不同请求在不同时间进入和退出批次；讲显存容量时，展示权重、缓存和临时空间逐步占用。技术示意必须与实际机制一致。

## 7. 示意与数据真实性

- 模拟聊天界面、请求数量和性能指标应标明“演示”或“示意”。
- 不得将简化假设描述成所有硬件/框架的固定行为。
- 如果用固定数量演示 GPU 并发，应说明这是为了理解队列的简化模型，真实并发能力受模型、Batch、序列长度、显存、调度策略和硬件等影响。
- 不编造真实性能数据或优化收益。
- 结构示意图中的箭头应表达真实方向或关系，不作为装饰。

## 8. 锚点、状态和播放器兼容

**先理解现有项目，再决定如何实现。**

- 保留已有场景编号、步骤编号、内容生成流程和 URL 定位。例如 `S07.0` 为页面初态，`S07.1`–`S07.3` 为后续状态，`#S07/3` 定位到第三步。
- `Sxx-Axx` 只是新项目可选格式，不强制迁移。
- 内部 ID、口播标记和 URL 可以采用不同格式，只要映射正确。
- Scene → Step 是常见组织方式；连续动画可由某个步骤启动，不要求独立 Timeline 对象、ID 或专用控件。
- 如果项目固定每页四个状态（包括 `.0` 初态），新增或合并步骤时必须同步检查内容源、口播导出、校验器、渲染逻辑和导航/旧链接。
- 当单个场景内容过多时，可以增加场景/页面，而不是强行突破原有状态数限制；是否增加页面应结合课程结构与项目约束判断。

### 播放能力按需复用

- 基础能力通常包括下一步/上一步、页面切换、暂停（有连续动画时）、整页重播/复位和录制模式。
- 已有步骤条点击或 URL 定位足够时，不增加输入任意动作 ID 的控件。
- 单个动作独立重播、任意 ID 搜索、独立 Timeline 管理均为可选功能，只有真实需求存在时才开发。
- 讲师模式可显示口播、锚点和快捷键；录制模式隐藏备注、控制栏和调试信息。
- 状态必须可复现；回退、重播和切换场景后不能残留旧状态。

## 9. 视觉设计要求

- 沿用用户已经认可的字体、颜色和视觉语义；不要为追求“纪录片感”而无故重做视觉系统。
- 不要将所有内容放进卡片或方框。
- 让主体对象有足够的画面面积，避免标题、说明和控制面板挤压主视觉。
- 文字只保留观众理解当前画面所需的信息；完整解释交给旁白。
- 录制模式下不显示讲师备注、调试面板和不必要的播放控件。
- 按目标分辨率检查文字、代码和图形的清晰度，默认按 16:9 / 1080p 验收。

## 10. 实际运行验收

不生成独立审查报告，但必须内部检查：

- 关键场景初始状态、每个重要中间状态和最终状态。
- 连续动画开始、暂停、结束和复位。
- 上一步、下一步、整页重播和跨页恢复。
- 口播触发锚点与 HTML 状态映射。
- 录制模式是否隐藏所有讲师辅助 UI。
- 是否存在口播讲多个事件而画面静止、画面只显示抽象结论的问题。
- 是否有文字溢出、元素遮挡、过低对比度或 1080p 下无法阅读的代码。
- 模拟数据和简化假设是否有明确标识。

尽可能使用浏览器实际运行和截图检查，而不是只检查源代码。无法运行或无法验证时，明确说明限制，不得声称测试通过。

## 11. 修改已有项目的优先级

1. 先理解现有项目架构、内容源、锚点、校验脚本和播放器。
2. 优先识别教学任务过载、长口播配静态图、具体旁白配抽象图等高影响问题。
3. 优先补足对象、操作、过程和结果，再调整局部视觉细节。
4. 只有口播本身不准确、不自然或顺序不合理时才重写口播；不要为了迁就空洞画面而把讲解改得抽象。
5. 保留成熟的设计系统和播放机制，做最小但有效的工程改动。
